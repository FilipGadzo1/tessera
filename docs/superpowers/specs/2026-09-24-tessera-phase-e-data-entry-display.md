## 0. Carry-over: forced-colors focus visibility (Task 0, first)

Problem (Phase D final review): Tailwind v4 `outline-hidden` is `outline-style: none` normally but, inside `@media (forced-colors: active)`, `outline: 2px solid transparent; outline-offset: 2px`. Chromium paints that transparent outline as CanvasText, so every control using the toggle focus pattern (`outline-hidden … focus-visible:outline-2 focus-visible:outline-solid`) shows a permanent outline in forced colors and focus is not distinguishable by outline (WCAG 2.4.7).

Target:
- **Interactive controls and items** (Button, Checkbox, Switch, Radio, Tabs tab + panel, Accordion trigger, text fields, Select trigger, menu/select items, and every Phase E control): replace `outline-hidden` with `outline-none` (`outline-style: none` in every mode). The focus state keeps `outline-2 outline-solid` (text fields `outline-1`), so in forced colors the ring appears only on focus, painted in a system colour. Where the focus colour would equal the unfocused border colour in forced colors, add `forced-colors:focus-visible:outline-[Highlight]` (text fields: `forced-colors:focus:outline-[Highlight]`).
- **Menu / Select items**: the highlighted item keeps its `data-highlighted:outline-2 outline-solid -outline-offset-2` (transparent normally, a system colour in forced colors); unhighlighted items must show no outline in forced colors.
- **Surfaces** (`popupSurface`, dialog popup, toast root): keep `outline-hidden`. A forced-colors outline on a floating surface is a desirable border there, and the surfaces are not focus targets except the toast root, which adds its own focus ring — verify it stays distinguishable (outline width or colour differs on focus); if not, give it `forced-colors:focus-visible:outline-[Highlight]`.
- **Segmented tabs**: an active segmented tab under hover must keep `HighlightText` text in forced colors (`forced-colors:data-active:hover:text-[HighlightText]`), otherwise the hover text colour wins against the `Highlight` background.
- Update design-system-v2 §4 **Focus** so the rule reads `outline-none` (and drop the sentence claiming `outline-hidden` keeps focus visible in forced colors).
- Tests: a shared helper `emulateForcedColors(active)` in `test/` using Playwright CDP (`Emulation.setEmulatedMedia` with `forced-colors: active`), as Phase D's Progress/Tabs tests did. For each control family: unfocused → computed `outline-style: none`; Tab-focused → `solid` with width ≥ 1px. Plus the segmented hover text test. The existing normal-mode focus tests must keep passing unchanged.

## 2. Details

**Breadcrumb** (shadcn-shaped, server-safe)
- `Breadcrumb`: `<nav aria-label="Breadcrumb">` (label overridable).
- `BreadcrumbList`: `<ol>` `flex flex-wrap items-center gap-1.5 text-sm text-muted-foreground`.
- `BreadcrumbItem`: `<li>` `inline-flex items-center gap-1.5`.
- `BreadcrumbLink`: `<a>` (supports `render` via Base UI `useRender` only if that is server-safe; otherwise an `asChild`-free design: accept `render?: React.ReactElement` and clone — implementer picks the server-safe option and records it) `rounded-sm transition-colors hover:text-foreground` + the toggle focus pattern + `cursor-pointer`.
- `BreadcrumbPage`: `<span aria-current="page">` `font-medium text-foreground`.
- `BreadcrumbSeparator`: `<li role="presentation" aria-hidden="true">` default chevron-right icon (inline SVG, `size-3.5`), children override.
- `BreadcrumbEllipsis`: `<span role="presentation" aria-hidden="true">` with a "more" icon and a visually hidden "More" text; callers wrap it in a Menu trigger when collapsing.
- *Amended in Task 1*: `BreadcrumbLink`'s `render` escape hatch is a plain `render?: React.ReactElement` cloned with `cloneElement` (merging `data-slot` and `className`, later Tailwind utilities win), not Base UI's `useRender`. `useRender` (`@base-ui/react/use-render`) delegates straight to the internal `useRenderElement` hook, so it is not hook-free/server-safe; using it would force `"use client"` onto Breadcrumb, contradicting its server-safe row above. `BreadcrumbEllipsis`'s container classes (`flex size-9 items-center justify-center`) aren't given verbatim above; picked a reasonable shadcn-shaped default since the row above only specifies content and semantics, not layout classes.

**Pagination** (server-safe)
- `getPaginationRange({ page, pageCount, siblings = 1, boundaries = 1 }): Array<number | "ellipsis-start" | "ellipsis-end">` — pure, unit-tested (edges: pageCount 0/1, page at start/end, no ellipsis when the gap is exactly one page — show the page instead).
- `Pagination`: `<nav aria-label="Pagination">` `mx-auto flex w-full justify-center`.
- `PaginationContent`: `<ul>` `flex flex-row items-center gap-1`. `PaginationItem`: `<li>`.
- `PaginationLink`: `<a>` styled with `buttonVariants({ variant: isActive ? "outline" : "ghost", color: "neutral", size: "icon" })`; `isActive` sets `aria-current="page"`. A `render` escape hatch for `<button>` / router links (same decision as BreadcrumbLink). Disabled: `aria-disabled="true"` + `data-disabled` (no `href`) — keeps focusability rules sane for links.
- `PaginationPrevious` / `PaginationNext`: PaginationLink with `size="md"`-width, chevron + visible "Previous"/"Next" text (text hidden below `sm:` with an `aria-label` kept), `aria-label="Go to previous page"` / `"Go to next page"`.
- `PaginationEllipsis`: `<span aria-hidden="true">` `flex size-10 items-center justify-center` + sr-only "More pages".
- *Amended in Task 1*: `PaginationLink` and `BreadcrumbLink` share the same `render` decision (see the Breadcrumb amendment above) — a cloned `render?: React.ReactElement`, not `useRender`. `PaginationLink` also gained a `size` prop (`ButtonVariantProps["size"]`, default `"icon"`) so `PaginationPrevious`/`PaginationNext` can pass `size="md"` for the "size=`md`-width" pill this section describes: `md` and `icon` share the same `h-10` height, so the previous/next controls line up with the numbered links while getting the extra horizontal padding for their chevron + text.

**Table** (server-safe, shadcn-shaped)
- `Table`: wrapper `<div data-slot="table-container" class="relative w-full overflow-x-auto">` + `<table class="w-full caption-bottom text-sm">`. `className` goes to the table; `containerClassName` to the wrapper.
- `TableHeader` `<thead>` `[&_tr]:border-b`; `TableBody` `<tbody>` `[&_tr:last-child]:border-0`; `TableFooter` `<tfoot>` `border-t bg-muted/50 font-medium [&>tr]:last:border-b-0`.
- `TableRow` `<tr>` `border-b border-border transition-colors hover:bg-muted/50 data-[state=selected]:bg-muted` (+ `aria-selected` styling: `aria-selected:bg-muted`).
- `TableHead` `<th>` `h-10 px-3 text-left align-middle font-medium text-muted-foreground whitespace-nowrap`; prop `sort?: "ascending" | "descending" | "none"` → `aria-sort` (omitted when undefined).
- `TableCell` `<td>` `px-3 py-2.5 align-middle`. `TableCaption` `<caption>` `mt-4 text-sm text-muted-foreground`.
- `TableSortButton`: a `<button type="button">` inside `TableHead` — `-ml-2 inline-flex h-8 cursor-pointer items-center gap-1 rounded-md px-2 hover:bg-muted hover:text-foreground` + toggle focus pattern; prop `direction?: "ascending" | "descending" | "none"` picks the icon (arrow-up / arrow-down / arrow-up-down, `aria-hidden`). No hooks; `onClick` is the caller's.
- Density prop is YAGNI for now.

**Slider**
- `Slider` renders Root → Control → Track → Indicator + one `Thumb` per value (value array length; `defaultValue`/`value` number or number[]). Props pass through to Root; `color` (tone, default primary); `size` (`sm` track h-1 / thumb size-4, `md` default h-1.5 / size-5).
- Root `relative flex w-full touch-none select-none flex-col gap-2 data-disabled:opacity-50`; Control `flex h-5 items-center data-[orientation=vertical]:h-full…`; Track `relative h-1.5 w-full grow overflow-hidden rounded-full bg-muted` (vertical: `w-1.5 h-full`); Indicator `bg-tone`; Thumb `block size-5 cursor-grab rounded-full border-2 border-tone bg-background shadow-sm active:cursor-grabbing data-disabled:cursor-not-allowed` + toggle focus pattern (focus lives on the thumb's input — implementer verifies where Base UI puts focus and targets it, e.g. `has-focus-visible:`).
- Children slot above the control (like Progress): `SliderLabel` (Base UI `Slider.Label` if present, else `Field` naming) and `SliderValue` (`ms-auto text-sm tabular-nums text-muted-foreground`).
- Each thumb needs an accessible name: `getAriaLabel` / `thumbLabels?: string[]` for ranges.
- Forced colors: indicator `forced-colors:bg-[Highlight]`, track outline `forced-colors:outline forced-colors:outline-1 forced-colors:outline-[CanvasText]` (Progress parity), thumb border `forced-colors:border-[CanvasText]`.
- *Amended in Task 3*: reading `node_modules/@base-ui/react/slider/thumb/SliderThumb.js` confirmed the thumb renders a wrapper `<div>` plus a nested visually-hidden `<input type="range">`, and that this input — not the wrapper — receives focus; the thumb's focus ring is `has-[:focus-visible]:outline-2 has-[:focus-visible]:outline-solid` on the wrapper (plus `forced-colors:has-[:focus-visible]:outline-[Highlight]`, since the wrapper's unfocused border is forced to `CanvasText` and an un-forced `outline-ring` would otherwise resolve to the same forced colour, hiding the focus change — same rule as Task 0's `forced-colors:focus-visible:outline-[Highlight]`, adapted to the `has-[]` selector). `Slider.Root` also always renders `role="group"`, and a plain `aria-label`/`aria-labelledby` passed to `<Slider>` labels that group `<div>`, *not* the thumb's `role="slider"` input (verified against `SliderRoot.js` and `SliderThumb.js`: the input's name comes from `getAriaLabel`/`aria-label`/`aria-labelledby` given to `Slider.Thumb` itself, or its `labelId` context set by a `Slider.Label`/`Field`). So `Slider` forwards a solo thumb's `aria-label`/`aria-labelledby` down to its one `Slider.Thumb` (range sliders without `thumbLabels` fall back to the shared `SliderLabel`/`Field` name, same as Base UI's own default). `getAriaLabel` is per-`Slider.Thumb`, called with that thumb's own index, so one shared `(index) => thumbLabels[index]` function is passed to every thumb. The vertical track thickness per `size` (`sm` → `w-1`, `md` → `w-1.5`) mirrors the given horizontal `h-1`/`h-1.5` values since the spec only gave the `md` vertical width (`w-1.5`) explicitly.
- *Amended in Task 3, fix round 1 (review C1)*: `Slider.Thumb` renders as a sibling of `Slider.Track`, both direct children of `Slider.Control` — not nested inside `Slider.Track` as this section's first bullet's "Track → Indicator" phrasing implied. `Slider.Thumb` is `position: absolute` and each thumb's cross-axis offset (`top`/`left` 50% + a `translate`) is percentage-relative to its nearest positioned ancestor; with the thumb inside `Track` (which is only as thick as the track, `h-1`/`h-1.5`, and clips with `overflow-hidden` for the indicator's rounded corners), the 16–20px thumb — and its focus ring — was clipped to that thin band (confirmed with `document.elementFromPoint` just inside the thumb's edge landing on `Slider.Control` instead of the thumb, and visually with a screenshot showing a sliver of the thumb). `Slider.Control` now carries `relative` so the thumb positions against the *control's* full `h-5`/`w-5` box instead, while `Slider.Track` keeps its own `relative overflow-hidden` for the indicator. `Slider.Indicator` is unaffected (it stays inside `Track`; its position/size come from Base UI's own inline styles, not from being a sibling of the thumbs).
- *Amended in Task 3, fix round 1 (review I2)*: a plain `aria-label` is now also passed to `Slider.Root` (its `role="group"` keeps a name even though nothing reads it via ARIA today, for parity with `aria-labelledby`, which already went to Root). A range slider (`thumbCount > 1`) with an `aria-label` but no `thumbLabels` no longer leaves every thumb unnamed: `Slider` derives a per-thumb name — two thumbs get `"<label> minimum"`/`"<label> maximum"`, three or more get `"<label> 1"`, `"<label> 2"`, … A range slider with only `aria-labelledby` (no `aria-label`) and no `thumbLabels` still falls back to Base UI's own default (every thumb shares that id's name), since an id can't be split into per-thumb text the way a label string can.

**NumberField**
- Parts: `NumberField` (Root, all Base UI props), `NumberFieldGroup`, `NumberFieldInput`, `NumberFieldIncrement`, `NumberFieldDecrement`, `NumberFieldScrubArea` (optional label scrub).
- Convenience: `NumberField` with no children renders Group → Decrement, Input, Increment (the common stepper). With children, it renders only the Root.
- Group: `textFieldBase`-look on the group (`inline-flex items-stretch overflow-hidden`), focus-within ring instead of focus (`focus-within:outline-1 focus-within:outline-solid focus-within:outline-ring focus-within:border-ring`), sizes sm/md/lg via `textFieldSizes` heights. Input: borderless `min-w-0 flex-1 bg-transparent px-3 text-center tabular-nums outline-none`. Buttons: `flex aspect-square h-full cursor-pointer items-center justify-center text-muted-foreground hover:bg-muted hover:text-foreground data-disabled:cursor-not-allowed data-disabled:opacity-50` with a border between (`border-field-border`), minus / plus icons, `aria-label` "Decrease" / "Increase" (Base UI may supply — verify).
- Works in `Field` (label names the input; invalid → danger border on the group), supports `format` (Intl.NumberFormatOptions), `min`/`max`/`step`, `readOnly`, `disabled`.
- *Amended in Task 4*: reading `node_modules/@base-ui/react/number-field/root/useNumberFieldStepperButton.js` confirmed the increment/decrement buttons render `tabIndex: -1` ("Keyboard users shouldn't have access to the buttons, since they can use the input element to change the value"), so they're excluded from the Tab order; the Tab-focus test targets the group's `focus-within` ring via the input, not the buttons directly, and there is no toggle-focus pattern on the buttons themselves. The same file confirms Base UI supplies `aria-label: 'Increase'/'Decrease'` on the buttons already, so Tessera's `NumberFieldIncrement`/`NumberFieldDecrement` don't set their own.
- *Amended in Task 4*: the Group's classes are written out directly rather than derived from `textFieldBase` by string surgery (the Select trigger's `.replace()` derivation is a known backlog weakness) — see `src/components/number-field/number-field-variants.ts`. It swaps `focus`/`disabled`/`read-only`/`aria-invalid` (which only match the native `<input>` `textFieldBase` targets) for `focus-within`/`data-disabled`/`data-readonly`/`data-invalid` (all present on the group's own `state`, confirmed by reading `NumberFieldGroup.js`, `NumberFieldRoot.js` and the shared `stateAttributesMapping.js`: the group receives the same Base UI `state` object as the Root, Input and stepper buttons, so Field's `invalid`/`disabled`/`readOnly` reach it the same way). "sizes sm/md/lg via `textFieldSizes` heights" is implemented as height-plus-text-size only (no horizontal padding): the group is edge-to-edge (`NumberFieldInput` carries its own `px-3`, and the stepper buttons are `aspect-square h-full`), so reusing `textFieldSizes`' padding verbatim would push the buttons in from the border.
- *Amended in Task 4*: the Group's transition list drops `outline-color` (unlike `textFieldBase`'s, which includes it): a debug repro (a bare `<div>` + nested `<input>` with the exact `textFieldBase`-derived class list) showed that transitioning `outline-color` on a `:focus-within` ring — an ancestor of the element that actually receives focus — leaves the ring's colour mid-interpolation (observed as `rgb(0, 0, 0)`, the pre-focus value) immediately after the focus change, unlike a `:focus` ring on the focused element itself (Input, Select trigger), which reflects the target colour immediately in the same synchronous check. This broke both the plain and forced-colors focus-within outline-colour assertions and, for real users, would show a momentary wrong-colour flash of the ring on Tab. Dropping `outline-color` from the transition list makes the ring colour snap; `outline-style`/`outline-width` still change together with it either way since Tailwind doesn't list them as transitionable properties here.
- *Amended in Task 4*: `NumberFieldScrubArea`'s classes (`cursor-ew-resize select-none text-sm font-medium`) aren't given verbatim in this section — it only says "optional label scrub" — so a minimal, sensible default was picked (a draggable label-sized hit target), consistent with the `ScrubAreaLabel` story wrapping a plain text label.
- *Amended in Task 4*: a plain `aria-label`/`aria-labelledby` passed to `<NumberField>` is forwarded to the convenience-rendered `NumberFieldInput` (Base UI's `NumberFieldRoot` renders an unlabelable `<div>`, so those props would otherwise land there and never reach assistive tech, the same class of problem Task 3 hit with `Slider.Root`'s `aria-label` only naming its `role="group"` wrapper). When children are passed instead, `NumberField` can no longer intercept them for its own subtree, so the caller sets `aria-label`/`aria-labelledby` directly on their own `NumberFieldInput`.
